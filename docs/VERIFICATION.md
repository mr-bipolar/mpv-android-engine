# Verification report

Everything here was produced in a sandbox with **no Android SDK/NDK/Gradle and no device**. The categories are kept apart on purpose.

## 1. Compiled successfully
* All library sources (`is.xyz.mpv.MPVLib`, 28 engine classes) and `docs/examples/UsageExample.java` compile with `javac 21 -source 8 -target 8`
  against a **real `android.jar` (API 34)**, obtained from the GitHub mirror `Sable/android-platforms` (not from an official SDK install).
* Tests compile and run on a plain JVM.
* **Not done:** Gradle / Android Gradle Plugin build, AAR packaging, R8/ProGuard run, lint. The `build.gradle` files are written against
  the versions upstream mpv-android uses (AGP 9.2.1, Gradle 9.4.1, compileSdk 36) but were never executed.
* **Not done:** compiling the native code for Android (no NDK). Instead, upstream's six real JNI C++ files (`main, render, log, jni_utils,
  property, event`) were syntax-compiled with g++ against the header generated by `javac -h` from our `MPVLib.java`, and all 7 static
  callback descriptors the native code looks up were matched in our class (`docs/test-logs/jni-contract-check.log`). Same result with the optional patch applied.
  `thumbnail.cpp` could not be compiled (needs Android bitmap/swscale headers). This proves the Java <-> native *signatures* agree; it does not run anything.

## 2. Engine initialized
* **Real libmpv 0.37.0 / FFmpeg 6.1.1 on Ubuntu 24.04:** initialised through (a) small C programs calling the libmpv API directly (`verify/t1.c, t2.c, t3.c`:
  error codes, `option-info/*`, JSON string conversion of node properties, runtime property settability) and (b) the desktop `mpv` process driven
  through its JSON IPC by `MpvIpcBackend` (test-only), which runs the **real `MpvPlayer` code**.
* **Not done:** initialisation through JNI on Android (`libplayer.so` + `libmpv.so` never built or loaded). The IPC path differs from JNI in: typed IPC values
  vs JNI conversions, options applied after the core is running, the end-file reason delivered through IPC.
* Names/ranges: every option/property/command used (`verify/names.txt`) was checked in mpv **master** docs and against 0.37 (`docs/test-logs/mpv-names-check.log`).
  mpv-android builds mpv from master, so master docs are the reference; where 0.37 differs the engine adapts or reads the build's own value
  (`loadfile` argument layout, `video-aspect-override` default, `sub-pos` max via `option-info`).

## 3. Actual media playback tested (desktop, software decoding, null video/audio output)
16 integration tests, all passed (`docs/test-logs/integration-tests-desktop-mpv.log`): local mp4 play/seek/pause/speed/volume/EOF/restart; tracks and
subtitles on an mkv with 2 audio + 1 subtitle track, external subtitle and external audio; geometry settings read back from mpv; HLS VOD; playlists with
auto-advance, a broken entry, previous/next; HTTP headers/User-Agent/Referer delivered to a local server; screenshot file written.
**Not tested:** MediaCodec hardware decoding, GPU rendering/surface, Android audio output, real codecs/containers beyond H.264/AAC/SRT test material.

## 4. Live-stream buffering tested (simulated only)
* Source: `ffmpeg -re` writing a rolling HLS playlist (2 s segments, 6 in the window, no `#EXT-X-ENDLIST`) served by a local HTTP server.
* Finding that shaped the design: **live HLS reports a growing duration with `seekable=no`** (so "duration present => VOD" would be wrong).
* Profiles, buffered-ahead of the playhead after ~6 s: STABLE ~4.0 s, BALANCED ~3.9 s, LOW_LATENCY ~0.0 s (an earlier run: 5.9 / 5.9 / 0.1). Window too short to separate
  STABLE from BALANCED; treat as direction, not as figures.
* Outage test: server stopped for ~5 s mid-playback, restarted: state went PLAYING -> BUFFERING -> PLAYING and the stream continued (duration kept growing) with
  no application retry needed (FFmpeg/mpv handled it). Longer outages, other protocols (RTMP/RTSP/UDP/MPEG-TS) and real IPTV providers were **not** tested.
* Unreachable network stream: 1 + 2 retries with exponential backoff, then `ERROR`, with mpv's error log lines attached; identical result whether the exact
  end-file reason (patch) or the inferred one is used.

## 5. Not verified (explicit list)
Android device/emulator runs of anything; the Gradle build; native build from source; MediaCodec zero-copy/copy-back; surface lifecycle and background audio;
`content://` handling; HTTPS with mbedTLS + `tls-ca-file`; memory behaviour under load/soak; real IPTV providers and protocols other than HTTP/HLS;
subtitle formats beyond SRT; audio device switching; screenshots with a real surface; behaviour of newer mpv master options than those documented here.

## Defects found by this verification (and fixed)
* `demuxer-lavf-o-add` is **not** accepted by `mpv_set_option_string` (error -5) -> option lists are composed in full.
* Header values with `,` are lost by mpv's `http-header-fields` -> now rejected with a clear error; per-file header lists replace the global list -> merged by the engine.
* `FILE_LOADED` can precede the `duration`/`seekable` property notifications -> values are read directly at that moment.
* `video-aspect-override=no` reads back as `0` on 0.37 (not the default) -> reset writes back the build's own default.
